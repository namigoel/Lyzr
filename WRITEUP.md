# Coverage Desk — write-up

## What I built

A workbench for a one-to-three-person research desk (an independent analyst, or a small RIA) that covers a handful of tickers and needs every rating change to be auditable: what changed, why, who signed off, and how to undo it cleanly if it was wrong. The agent researches and drafts; the human approves, edits, rejects, or rolls back. Nothing reaches the record without a human commit.

It runs on GitAgent as a literal git repository, not a metaphor. A ticker's recommendation is `memory/coverage/<TICKER>.md`; its history is `git log` on that file. The agent drafts on a review branch and stops — it has no path to `main`. Approving a draft is a real merge; rejecting one deletes the branch and logs why; rolling back a bad call is a real `git revert`, sitting in the log next to the mistake it corrects, not silently erased.

## Who it's for

A solo or small-desk equity analyst who currently keeps coverage in a shared doc or spreadsheet and has no good answer to "why did we downgrade this, and when did the thesis actually change?" That question is exactly what a git history answers for free, if the recommendation itself lives as a file instead of a cell you overwrite.

## The decisions I made

**Treat the recommendation as memory, not as an agent output that gets logged elsewhere.** The obvious version of this app has the agent chat with you and occasionally save a summary to a database. I made the recommendation file *be* the memory layer from the gitagent spec — every revision is a commit, every rollback is a revert, every approval trail is `git log`. This is the one decision the rest of the app follows from; it's also the reason a generic chatbot wrapper couldn't do this — there's no branch, no diff, no revert in a chat log.

**No LLM API key required to run it.** The brief explicitly said this isn't a demo-with-an-LLM-attached exercise, and I took that at face value: the interesting surface is the harness, not the model. `skills/*/SKILL.md` document the LLM-driven version of research → draft → mandate-check for real `opengap run --adapter claude` use; the workbench ships a deterministic implementation of the identical contract (real live market data via a public API, a real mandate-check gate, real git operations) so it runs with zero setup and zero cost for review. Swapping the deterministic drafting step for a Claude call is a small, isolated change (`server/lib/agentEngine.js`) — I chose not to make that swap in the time available because it would have added an API-key dependency to the reviewer's setup for a change that doesn't touch the part of the assignment being evaluated.

**Segregation of duties is enforced at the interface, not just declared in YAML.** `agent.yaml` declares maker (agent) / checker (human) roles per the gitagent compliance spec, but I didn't stop at declaring it — the server has no route that lets an agent-authored branch reach `main` without passing through a human-invoked `/approve` endpoint, and that endpoint re-runs the mandate check even if the analyst edited the content first. The policy is real, not decorative.

**The seed history is disclosed, not hidden.** `agent-workspace/` — the actual running gitagent repository — is generated by `seed/seed.js` with backdated commits telling one coherent incident (a good call, an overreach, a revert, a mandate amendment written in response). I could have shipped a frozen `.git` directory to make the history look more "found," but a nested git repo inside a git repo is fragile and, more importantly, would misrepresent what's demo data versus what's this submission's own commit history. The generator is the honest version of that same demo.

## What I'd do with a full week

- **Wire the deterministic drafting step to a real LLM call** (Claude, via the SDK) behind the exact same skill/mandate-check contract, so the thesis prose is actually synthesized rather than templated, with the deterministic path kept as a fallback/offline mode.
- **Multi-branch scenario compare** — the Diff tab compares two points in one file's history; I'd add a real side-by-side "bull-case branch vs bear-case branch" view for the same ticker, since gitagent's branching model supports it and the UI doesn't yet expose it.
- **A second analyst identity and a real approval quorum** for the handoff workflow in `DUTIES.md` (right now there's one checker; the spec supports requiring more).
- **Persist the fetched quote as its own knowledge artifact** with its own retrieval history, instead of only living inside the thesis's Data section, so "what did the market look like at every decision point" is queryable across the whole portfolio, not just per-ticker.
- **Real-time price ticking** in the Data tab instead of fetch-on-research, and a small backtest view: replay each historical call against what actually happened afterward.

## What's broken, and why I left it that way

- **The signal model is a heuristic, not a validated one.** It's a single momentum read plus a static sector note, deliberately declared as such in every thesis's Signal Trace and in `compliance/risk-assessment.md`. Building a real signal model wasn't the assignment; building the harness that makes a signal model's output auditable and reversible was.
- **Reverting a ticker's very first (initiating) commit always fails with a merge conflict** by design of `git revert` itself — there's nothing to revert *to* before a file's creation. The server catches this and aborts the revert cleanly instead of leaving the repo in a broken state, and the UI hides the "revert" action on that one commit. What's still unguarded: reverting a commit several revisions deep, out of order, can conflict with commits that landed after it for unrelated reasons (git's normal behavior, not a bug I introduced) — the server surfaces the conflict as an error rather than crashing, but the UI doesn't yet explain *why* to the analyst beyond the raw message.
- **No auth, no multi-user concurrency control.** This is a single-analyst desk tool as scoped; two people clicking "approve" on the same branch at the same time would race. Fine for the assignment's scope, not fine for a real desk with more than one seat.
- **The mandate-check logic is duplicated in spirit between `hooks/scripts/mandate-check.js` (required directly by the server) and `skills/mandate-check/SKILL.md` (the prose version for an LLM-driven run).** They're meant to enforce the same rule set, but nothing currently tests that they agree. Fine for a 48-hour scope; a real CI check comparing them would be the first thing I'd add.
